# 工具选择与能力映射

**何时读取：** 首次选择执行后端、上游给出多个允许工具、MCP 是否可用不清楚，或拟从 MCP 切换到 CLI/Python/WSL 时。

## 先确认事实

从当前会话的工具目录或实际 MCP 初始化/列举结果发现工具，再查所选 handler 的参数、返回和限制。分别记录三层：

1. 控制层：MCP server/包是否可达，列出的 handler 名称与 server 版本；
2. 求解层：handler 实际调用的 solver、可执行路径、版本、许可证/设备状态及所需物理能力；
3. 运行层：Python、容器、WSL、工作目录、依赖及读写路径是否真实可用。

MCP handler 存在不等于 solver 可运行；能 import 适配器也不等于外部可执行文件可用。用轻量 doctor、version、help、dry-run 或最小合法输入探测，但不要把探针当目标规模结果。

## 选择顺序

优先选择上游指定且能力匹配的成熟 MCP/求解框架。比较的不是工具名，而是：所需维度/单元/物理/BC/耦合是否支持；能否输出指定原生字段、association 和时间覆盖；能否留下日志、checkpoint 与批量工况记录；预算内是否可运行。

若没有实际 MCP，且上游未禁止替代，可使用兼容的成熟 CLI、Python API、容器或 WSL；在 manifest 中写明实际路径，不得伪装成 MCP。短 Python/壳脚本负责参数展开、原生模型输入、调用、格式转换和索引，不重新发明 solver。替代只改变数值实现时，记录方法/输出映射并按目标量核验，不因网格、时间步或离散不同自动拒算。替代若改变物理方程、闭合或验证观测，向准备/上游负责人请求调整；不要把科学含义变化写成透明替代。

openPASO 仅在实际被选择时检查 `doctor`、MCP 工具枚举和外部 solver 三层，并在同一会话保存 review/refusal/run receipt；它不是硬依赖。任何专用 verifier 只能用于其文档覆盖的方程、坐标权重、BC 和字段位置，不适用就记录 `NOT_APPLICABLE`，不得强行转换后称已验证。

## 选择记录

在 manifest 中写下候选、探测证据、选择理由、实际版本和未满足能力。若上游指定工具不可用而替代会改变科学含义，返回 `FAILED` 或已有有效结果时 `PARTIAL`，并给出解除条件；不要自行扩张授权安装、改模型或换物理。
